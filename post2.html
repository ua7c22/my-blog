基于 Spring Cloud 的微服务电商平台实践

从单体到微服务：服务拆分、治理与分布式事务

发布于 杨林 于 2026-10-28

当单体应用越做越大，改一行代码要整个部署、某个模块挂了全站陪葬，就说明该拆微服务了。本文复盘我把一个电商单体拆成微服务的过程，技术栈基于 Spring Cloud Alibaba。

服务怎么拆

按照业务域拆分出用户、商品、订单、库存、支付等独立服务，每个服务拥有自己的数据库，服务之间通过接口通信，互不越界。拆分的核心原则是「高内聚、低耦合」，按领域而不是按功能切。

注册与配置：Nacos

服务多了，互相怎么找到对方、配置怎么统一管理就成了问题。我用 Nacos 同时承担注册中心和配置中心，服务启动自动注册、配置动态刷新，运维成本大幅下降。

统一入口：Gateway 网关

对外只暴露一个网关，网关负责路由转发、统一鉴权、限流和日志。客户端不再直连各服务，内部服务拓扑对前端完全透明，安全性和可维护性都更好。

远程调用：OpenFeign

服务间调用用 OpenFeign 声明式完成，一个接口就是一次远程调用，自带负载均衡：

@FeignClient(name = "order-service")
public interface OrderClient {
    @PostMapping("/order/create")
    Result<Long> create(@RequestBody OrderDTO dto);
}

分布式事务：Seata

「下单」要同时写订单表和扣库存，跨了两个服务、两个库，传统事务失效。我用 Seata 的 AT 模式，把跨服务的操作纳入一个全局事务，最终保证数据一致。

流控降级：Sentinel

大促时某服务可能被压垮，进而拖垮整条链路。用 Sentinel 做限流、熔断和降级，核心接口过载时快速失败、兜底返回，保护系统不雪崩。

微服务不是银弹，拆分也带来了分布式复杂度。但掌握好拆分粒度与治理组件，它就是支撑业务长期演进的正解。这套架构我也整理了完整的部署脚本，后续文章再展开。
