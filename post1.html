高并发秒杀系统：从架构设计到落地

限流、削峰、防超卖，一次完整的秒杀实战复盘

发布于 杨林 于 2026-11-02

秒杀是电商领域最经典的超高并发场景：开抢的一瞬间，流量可能是平时的几十甚至上百倍。本文复盘我做的一个秒杀系统，技术栈为 Spring Boot + Redis + RabbitMQ + MySQL，目标是「扛得住、不超卖、不死机」。

三个核心难点

秒杀的难点可以归结为三件事：一是高并发下如何保证库存不被超卖；二是瞬时流量如何不把数据库打垮；三是大量无效请求如何被快速拦截，不占用宝贵资源。

整体架构分层

整个链路从外到内依次是：前端按钮防重（点击后置灰）→ Nginx 限流 → 网关做合法性校验 → 应用层 → Redis 预扣库存 → MQ 异步下单 → MySQL 最终落库。每一层都只做自己该做的事，把压力逐层消化掉。

防超卖：Redis + Lua 原子扣减

库存的判断与扣减必须是一个原子操作，否则两个请求同时读到「还有 1 件」，就会双双下单成功。我用 Redis 缓存库存，配合 Lua 脚本把「查库存 + 扣减」打包成一次原子执行：

-- Redis 原子扣库存（Lua 脚本）
local stock = tonumber(redis.call('get', KEYS[1]))
if stock and stock > 0 then
    redis.call('decr', KEYS[1])
    return 1
end
return 0

同时数据库层再用「乐观锁」兜底（update ... set stock = stock - 1 where stock > 0），保证即使 Redis 出现异常，也不会超卖。

削峰填谷：MQ 异步下单

如果每个请求都直接写数据库，再好的库也扛不住。我的做法是：Redis 扣减成功的请求，生成唯一订单号后投递到 RabbitMQ，后端按自身处理能力匀速消费，把「尖峰」拉成「平谷」，数据库压力骤降。

幂等与兜底

用户疯狂点击、消息重复消费，都可能导致重复下单。我用「唯一订单号 + Redis 去重」保证幂等；下单失败则回滚库存并告警。宁可少卖，不可超卖，这是秒杀的底线。

压测结果

用 JMeter 压测对比：裸 MySQL 架构 QPS 只有几百，且库存错误；换成 Redis + MQ 架构后，接口 QPS 稳定在 1 万以上，平均响应时间几十毫秒，库存零误差。

这套思路同样适用于抢票、限量领券、签到抽奖等任何「瞬时高并发 + 有限资源」的场景，希望对你有帮助。
